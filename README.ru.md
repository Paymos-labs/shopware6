# Paymos для Shopware 6

[English](README.md) | [简体中文](README.zh-CN.md) | **Русский** | [Español](README.es.md) | [Deutsch](README.de.md) | [Türkçe](README.tr.md)

Официальный платёжный плагин Paymos для Shopware 6. После установки в магазине появляется один способ оплаты — **Pay with crypto (Paymos)**, который переводит покупателя на страницу оплаты Paymos. Там он выбирает стейблкоин и сеть и отправляет перевод со своего кошелька. Транзакция заказа переходит в `paid` по подписанному вебхуку, когда перевод подтвердится в блокчейне — возврат покупателя на витрину ничего не решает.

## Требования

Указаны в `PaymosPayments/composer.json`:

- `shopware/core`: `~6.5.7 || ~6.6.0 || ~6.7.0` — Shopware 6.5.7 и последующие патчи 6.5, вся ветка 6.6 и 6.7
- `php`: `>=8.2`
- Витрина по HTTPS: подключение отклоняет базовый URL на обычном HTTP
- Аккаунт Paymos с открытым в дашборде проектом, который нужно привязать

Архив включает Paymos PHP SDK прямо внутри плагина, потому что Shopware не запускает Composer для зависимостей плагина при загрузке ZIP. В пакет также входят уже собранные ресурсы Administration для обеих схем Shopware — webpack для 6.5 и 6.6, Vite для 6.7 — поэтому собирать админку вручную не придётся.

## Установка

Скачайте `paymos-shopware6-<version>.zip` со страницы [Releases](https://github.com/Paymos-labs/shopware6/releases/latest) или из раздела **CMS integration** в дашборде Paymos. Корневой каталог внутри архива называется `PaymosPayments/` — именно такое техническое имя ожидает Shopware.

Через админку: откройте **Extensions → My extensions → Upload extension**, выберите архив, затем установите и активируйте плагин.

Из консоли, распаковав архив в `custom/plugins/`:

```bash
bin/console plugin:refresh
bin/console plugin:install --activate PaymosPayments
bin/console cache:clear
```

Активация создаёт и включает способ оплаты. Добавьте его во все каналы продаж, где он нужен, через **Sales Channels → ваш канал → Payment methods**. Способ остаётся доступным и после создания заказа, так что при неудачной попытке покупатель сможет оплатить заказ повторно, не собирая корзину заново.

Опубликованные архивы одинаковы для всех мерчантов и не содержат API-ключа, API-секрета, ID проекта, секрета вебхука, OAuth-токена или кода устройства — установка сама по себе ничего не подключает.

## Подключение

Плагин регистрирует собственный модуль Administration, и подключение находится именно там, а не в карточке конфигурации расширения.

1. Выберите в дашборде Paymos проект, через который должен работать магазин. Привяжется именно открытый сейчас проект — второго выбора плагин не предлагает.
2. В Shopware перейдите в **Settings → Plugins → Paymos** и нажмите **Connect Paymos**.
3. Подтвердите URL магазина и проект в открывшейся вкладке. Если браузер заблокировал вкладку, это не тупик: страница покажет ссылку подтверждения и код пользователя.
4. Дождитесь сообщения `Paymos connected.`

Одно подтверждение сразу покрывает Sandbox и Live. Ваш единственный активный платёжный ключ используется повторно — или создаётся новый, если его ещё нет — и регистрируется вебхук инвойсов по адресу:

```text
https://your-store.example/paymos/webhook
```

Существующий вебхук используется повторно только при точном совпадении URL, категории и проекта; чужие настройки на этом адресе не перезаписываются.

Учётные данные хранятся в зашифрованном конверте AES-256-GCM внутри `SystemConfigService` с ключом на базе `kernel.secret` вашей установки и никогда не отдаются в браузер. Полей для ручного ввода секретов нет.

## Настройки по каналам продаж

Карточка настроек плагина читается с привязкой к ID канала продаж, поэтому оба поля задаются отдельно для каждого канала:

| Поле | По умолчанию | Что делает |
|---|---|---|
| Mode | `sandbox` | Какой набор учётных данных использует этот канал при оформлении заказа |
| Debug logging | off | Пишет обычную диагностику вебхуков в журнал Shopware; рабочие ошибки пишутся всегда |

Один канал продаж может спокойно тестироваться в Sandbox, пока другой уже принимает реальные платежи в Live. Сами ключи общие на всю установку: подключитесь один раз, а дальше переключайте каждый канал полем **Mode**. Точка приёма вебхуков не привязана к конкретному каналу и использует глобальное значение.

## Статусы транзакций заказа

| Событие Paymos | Транзакция заказа |
|---|---|
| Покупатель перенаправлен на страницу оплаты | остаётся `open` |
| `invoice.confirming` | `open` (открывается заново, если успела сменить статус) |
| `invoice.underpaid_waiting` | `open`; покупателю нужно доплатить остаток |
| `invoice.awaiting_payment` | `open`; учтённый платёж исчез после реорганизации сети |
| `invoice.paid`, `invoice.paid_over` | `paid` |
| `invoice.underpaid` | `failed` |
| `invoice.expired`, `invoice.cancelled` | `cancelled` |

Конечный автомат Shopware не разрешает прямые переходы между двумя финальными статусами, и плагин их не запрашивает. Уже отменённую (`cancelled`) транзакцию позднее событие `underpaid` не трогает; а транзакцию в статусе `cancelled` или `failed`, по которой всё-таки пришла оплата, плагин сначала переоткрывает и затем переводит в `paid`. Транзакция, дошедшая до `paid`, `refunded` или `refunded_partially`, никогда не откатывается назад.

Когда покупатель возвращается со страницы оплаты Paymos, обработчик смотрит на состояние транзакции, а не на параметры URL. Если вебхук ещё не дошёл, транзакция остаётся как есть: выброс исключения отправил бы покупателя на страницу ошибки и отменил платёж, который вот-вот подтвердится. Нажатие ссылки отмены после того, как оплата уже прошла, её не отменяет.

## Проверка перед запуском в рабочем режиме

1. Оставьте **Mode** в Sandbox для тестируемого канала продаж и оформите заказ.
2. Откройте этот инвойс в дашборде Paymos (также в режиме Sandbox) и нажмите **Pay Full**, **Pay 50%**, **Pay 150%** или **Cancel**. Каждая кнопка запускает реальные события жизненного цикла без движения средств.
3. Проверьте статус транзакции заказа и журнал Shopware при включённом Debug logging.
4. Переключите **Mode** этого канала на Live. Рабочие ключи пришли вместе с тем же подтверждением, повторное подключение не требуется.

## Вебхуки и восстановление

`POST /paymos/webhook` — маршрут витрины, поэтому уведомления приходят на домен витрины. Подлинность проверяется по заголовку `X-Webhook-Signature` — шестнадцатеричный HMAC-SHA256 от `{timestamp}.{body}`; при неверной подписи или устаревшей метке времени возвращается `401`. Заголовок `X-Webhook-Id` неизменен при повторах, поэтому дубликаты подтверждаются без изменения заказа. Прежде чем финальное событие применится, инвойс запрашивается обратно из Merchant API и сверяется с сохранённым снимком.

Цикл доставки включает 11 попыток за примерно 16 часов. На случай, если проблема длилась дольше, в плагине есть консольная команда:

```bash
bin/console paymos:reconcile
```

Она повторно запрашивает открытые инвойсы и ожидающие возвраты и проводит их через те же защищённые проверки, что и вебхук. В рабочем магазине запускайте её по cron каждые несколько минут.

## Возвраты

Плагин поддерживает нативные возвраты через Paymos Merchant API (`/v1/refunds`) в двух режимах:

- `full` — возврат полной оплаченной суммы инвойса;
- `overpayment` — возврат только переплаты по транзакции `invoice.paid_over` с сохранением оплаченного статуса заказа.

Средства возвращаются строго на проверенный адрес кошелька `first_sender`, зафиксированный Paymos при оплате инвойса. Вручную адрес получателя не вводится, а произвольные частичные возвраты и неподтверждённые ручные переводы статусов возврата для транзакций Paymos блокируются защитным механизмом плагина.

В админке Shopware откройте **Settings → Plugins → Paymos**, введите **Order transaction ID** в карточке **Paymos refunds** и выберите **Full refund** (`full`), **Refund overpayment** (`overpayment`) или **Check status**. Shopware переводит транзакцию заказа в `refunded` (при `full`) или записывает заметку о возврате переплаты только после подтверждения статуса `completed` от Paymos через `POST /paymos/webhook` или `bin/console paymos:reconcile`. Запускайте команду по cron каждые несколько минут, чтобы не терять пропущенные вебхуки. Кнопка **Check status** только показывает текущее состояние — она не запускает сверку и не применяет возвраты. В режиме Sandbox финальные исходы возврата (`completed`, `failed`, `cancelled`) можно симулировать без движения средств.

## Обновление Shopware

В версиях 6.5 и 6.6 используется асинхронный интерфейс обработчика платежей, а в 6.7 его заменил `AbstractPaymentHandler`. Один архив содержит оба варианта и автоматически выбирает API текущего ядра, но сам обработчик записывается в способ оплаты в момент установки. После перехода магазина на новую мажорную версию отключите и снова активируйте плагин: повторная активация обновит привязку обработчика, и способ оплаты снова заработает. Способ всегда определяется по техническому имени `paymos_crypto`, которое не меняется между версиями.

## Решение проблем

**В Settings нет пункта Paymos.** Модуль Administration берётся из собранных ресурсов плагина. Выполните `bin/console assets:install` и `bin/console cache:clear`, затем жёстко обновите страницу админки.

**Способ оплаты не виден при оформлении заказа.** Он создан и включён, но Shopware показывает только способы, добавленные в конкретный канал продаж. Добавьте Paymos в список способов оплаты нужного канала и убедитесь, что правила корзины не исключают его для вашего тестового заказа.

**Подключение не проходит из-за URL магазина.** Принимается только `https://`, а адрес собирается из того запроса, который видит сам Shopware. Если TLS завершается на обратном прокси, настройте передачу схемы через trusted-proxy в Shopware — иначе Shopware по-прежнему видит `http://`, и подтверждение отклоняется.
